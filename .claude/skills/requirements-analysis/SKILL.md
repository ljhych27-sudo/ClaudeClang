# 요구사항 분석 (A-SPICE SWE.1)

## 산출물
| 파일 | 내용 |
|---|---|
| `docs/requirements/software_requirements.md` | 기능·비기능 요구사항 명세 (SWR-*) |
| `docs/requirements/safety_requirements.md` | 기능안전 요구사항 명세 (SSR-*) — **반드시 별도 문서** |
| `docs/traceability.md` | 추적성 매트릭스 (요구사항 행 추가) |

ID 체계는 `CLAUDE.md`의 "ID 체계"를 따른다.

## 절차
1. **입력 수집**: 사용자 요구, 시스템 요구, 인터페이스 정의, 표준·법규를 확인한다. 출처를 알 수 없는 요구는 만들지 말고 사용자에게 묻는다.
2. **분류**: 각 요구를 아래 트리로 분류한다.
   ```
   요구사항
   ├─ 기능 요구사항 (SWR-F)        : 시스템이 "무엇을" 하는가
   │   └─ 기능안전 관련이면 → SSR로 safety_requirements.md에 작성, SWR-F에는 SSR 참조만
   └─ 비기능 요구사항
       ├─ 품질 (SWR-Q)             : ISO 25010 특성 중 하나에 반드시 매핑
       ├─ 제한 (SWR-L)             : 자원·성능 한계 (메모리, 실행 시간, 스택, 주기 등)
       └─ 제약 (SWR-C)             : 설계·구현 선택을 제한 (언어, 컴파일러, 표준, OS, 라이브러리 등)
   ```
3. **ISO 25010 매핑** (품질 요구사항): 아래 8개 특성과 하위 특성 중 하나를 `Quality:` 필드에 명시한다.
   - 기능 적합성(완전성·정확성·적절성) / 성능 효율성(시간 반응성·자원 활용·용량)
   - 호환성(공존성·상호운용성) / 사용성 / 신뢰성(성숙성·가용성·결함 허용·복구성)
   - 보안성(기밀성·무결성·부인방지·책임추적·진정성) / 유지보수성(모듈성·재사용성·분석성·수정성·시험성)
   - 이식성(적응성·설치성·대체성)
4. **명세 작성**: 아래 템플릿으로 작성한다. 모든 요구는 하나의 문장, 하나의 요구(atomic), "shall/해야 한다" 형태, 검증 가능한 수치 기준을 갖는다.
5. **추적성**: `docs/traceability.md`에 요구사항 행을 추가한다. 하위 산출물 열은 비워 두되, 비어 있는 칸은 이후 단계에서 반드시 채워야 할 미결 항목이다.
6. **시스템 테스트 입력**: 이 문서는 `sw-system-test-case` 스킬의 입력이다. 수용기준(Acceptance)은 외부 인터페이스에서 관찰 가능한 값으로 쓴다 (시스템 테스트 요구사항 커버리지 100% 기준).
7. **리뷰**: `aspice-reviewer` 서브에이전트(`review` 스킬)로 요구사항 체크리스트 리뷰를 수행한다.

## 요구사항 템플릿
```markdown
### SWR-F-001 <짧은 제목>
- Statement: 시스템은 <조건>일 때 <동작>을 <수치 기준> 내에 수행해야 한다.
- Type: Functional | Quality | Limit | Constraint
- Quality: (Quality일 때) ISO 25010 <특성>/<하위 특성>
- Source: <상위 요구 ID 또는 출처 문서>
- Safety: None | SSR-NNN (기능안전 관련 시 별도 문서 참조)
- Rationale: <이 요구가 필요한 이유>
- Verification: Test | Analysis | Inspection | Demonstration
- Acceptance: <합격 기준 — 측정 가능한 값>
- Status: Draft | Reviewed | Approved
```

기능안전 요구사항(`safety_requirements.md`)은 위 필드에 `ASIL/SIL:`, `Safety Goal:`, `Safe State:`, `FTTI:`(해당 시)를 추가한다.

## 품질 규칙
- 모호어 금지: "빠르게", "충분히", "적절히", "등", "가능하면" → 수치·조건으로 바꾼다.
- 하나의 요구에 "그리고/또는"으로 두 요구를 묶지 않는다.
- 설계 해법을 요구로 쓰지 않는다 (제약 요구 SWR-C는 예외).
- 요구 간 충돌·중복을 발견하면 작성하지 말고 사용자에게 보고한다.
