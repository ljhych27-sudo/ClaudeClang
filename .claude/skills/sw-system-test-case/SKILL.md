# SW 시스템 테스트 케이스 생성

시스템 테스트의 목적은 **결함 발견**이다. 요구가 맞게 동작하는 한 가지 경우만 보이는 테스트는 결함을 거의 찾지 못한다. 경계, 무효 입력, 조건 충돌, 상태 전이, 시간 경계처럼 구현이 틀리기 쉬운 곳을 노린다.

## 입력

- 필수: SW 요구사항 사양서(이 저장소는 `docs/requirements/software_requirements.md`, 기능안전은 `docs/requirements/safety_requirements.md`). SWR/SSR ID(`CLAUDE.md` 6장 ID 체계), 요구 문장, 수용기준(Acceptance), 등급(ASIL/QM).
- 있으면 함께 읽는다: 외부 인터페이스(입력 범위·무효 조건, `docs/architecture/`), 상태 정의, 우선순위 결정표, 이유코드 표, OEM 질의서(`[잠정]` 항목), 추적표(`docs/traceability.md`).
- 요구사항이 주어지지 않았으면 지어내지 말고 입력을 요청한다.
- 시험 대상은 SW 전체를 외부 인터페이스로만 다루는 블랙박스다. 내부 함수 이름이나 구현 구조에 기대지 않는다.

## 절차

1. **요구 목록화.** SWR마다 입력 변수, 출력, 수용기준의 숫자 경계, 관련 상태, 등급을 표로 뽑는다.
2. **기법 선택.** 아래 표에서 SWR 성격에 맞는 기법을 고른다. ASIL 요구는 최소 3개 기법을 적용한다.
3. **케이스 작성.** 한 케이스는 한 가지 판정만 검증한다. 기대 결과는 관찰 가능한 출력값(출력 필드, 이유코드, 로그 항목, 시간)으로 쓴다.
4. **생성 조건 점검.** 아래 조건을 하나씩 확인하고 결과를 표로 남긴다.
5. **결과 보고.**

## 설계 기법

| 기법 | 적용 대상 | 작성 요령 |
|---|---|---|
| 동등 분할 | 모든 입력 | 유효 클래스마다 1개, 무효 클래스마다 1개. 무효 클래스는 하나씩만 무효로 만든다 |
| 경계값 분석 | 숫자 경계(속도, 시간, 건수) | 경계 −ε, 경계, 경계 +ε. ε은 입력 해상도(예: 0.1 km/h, 0.001 s). 실수 누적 오차가 나기 쉬운 값(예: 1.1 → 1.3 경과 0.2 s)을 포함 |
| 결정표 | 여러 조건이 겹치는 판정, 우선순위 | 결정표 각 행이 이기는 케이스 + 인접 행 두 조건이 동시에 성립하는 충돌 케이스 |
| 상태 전이 | 상태가 있는 요구 | 모든 유효 전이 1회, 각 상태에서 허용되지 않는 이벤트, 초기 상태, 연속 전이(왕복) |
| 시간·순서 | "~이내", "다음 주기", 유지 시간 | 마감 직전·직후, 이벤트 순서 뒤바꿈, 같은 주기 동시 발생 |
| 오류 추측 | 입력 신뢰성, 고장 | 누락, 타입 오류, NaN/무한대, 미등록 열거 값, 오래된(신선도 초과) 입력, 입력 복구 후 동작 |
| 용량·지속 | 버퍼, 로그 건수 | 한계 −1, 한계, 한계 +1(가장 오래된 항목 제거 확인) |

## 생성 조건

결과를 내기 전에 모두 만족해야 한다.

1. **추적성:** 모든 SWR에 케이스가 1개 이상 있다. 모든 케이스는 SWR ID를 1개 이상 가진다.
2. **수용기준 완전성:** SWR의 수용기준 항목마다 그것을 직접 검증하는 케이스가 있다.
3. **경계:** 숫자 경계가 있는 요구마다 경계 −ε / 경계 / 경계 +ε 세 케이스가 있다.
4. **무효 입력:** 입력 필드마다 무효 클래스 케이스가 1개 이상 있다.
5. **우선순위 충돌:** 결정표가 있으면 모든 행에 대해, 그 행과 더 높은 우선순위 행이 동시에 성립하는 케이스가 있다.
6. **상태:** 상태 전이가 있는 요구는 모든 유효 전이와 초기 상태 케이스가 있다.
7. **기대 결과 구체성:** 기대 결과가 숫자·열거 값·이유코드로 쓰여 있다. "정상 동작", "적절히 처리" 같은 표현은 쓰지 않는다.
8. **재현성:** 사전 조건(초기 상태, 시각, 직전 입력)과 입력 순서가 다른 사람이 그대로 실행할 수 있을 만큼 구체적이다.
9. **[잠정] 표시:** 잠정 요구를 검증하는 케이스는 `[잠정](Q-xx)`을 표시한다. 회신에 따라 기대 결과가 바뀔 수 있기 때문이다.
10. **중복 없음:** 같은 클래스·같은 경계를 같은 목적으로 검증하는 케이스가 두 개 이상 있지 않다.

## 출력 양식

사용자가 양식(템플릿 파일 또는 형식)을 주면 그 양식을 그대로 쓴다. 없으면 아래 양식을 쓰고, 저장 경로는 `docs/test/system_test_spec.md`로 한다.

```markdown
# SW 시스템 시험 명세서

## 1. 개요
- 대상, 입력 문서(버전), 시험 환경(PC/SIL, Docker 이미지 `claudeclangbuild`, GoogleTest), 미검증 범위(HIL, 실차, 실시간 타이밍)

## 2. 시험 케이스

### STC-001 <제목>
| 항목 | 내용 |
|---|---|
| 요구사항 | SWR-F-nnn |
| 등급 | ASIL B / QM |
| 기법 | 경계값 분석 |
| 목적(노리는 결함) | 3.0 km/h를 '초과'가 아닌 '이상'으로 구현한 결함 |
| 사전 조건 | 초기 상태, 시각 t=0.000 s, ... |
| 입력·절차 | 1. ... 2. ... |
| 기대 결과 | 출력=LOCK, 이유코드=R-03, 로그 1건 추가 |
| 비고 | [잠정](Q-04) |

## 3. 추적표 (SWR → STC)
| SWR | 수용기준 | STC | 기법 |

## 4. 생성 조건 점검 결과
| 조건 | 충족 | 근거 |
```

케이스 ID는 `STC-nnn`을 쓰고, SWR 순서대로 묶는다.

## 구현과 실행 (이 프로젝트)

명세서의 모든 STC를 GoogleTest로 구현한다.

- 위치 `tests/system/`, `tests/system/CMakeLists.txt`에서 `gtest_discover_tests(<target> TEST_PREFIX "system.")`
- SW의 외부 인터페이스(공개 API)만 호출한다. 내부 헤더·`static` 함수·Mock 대체 금지.
- 테스트 함수마다 doxygen 주석: `@test STC-nnn <제목>`, `@trace <SWR/SSR ID>`, `@purpose`, `@input`, `@procedure`, `@expected`
- 실행·판정 (이미지 안에서): `bash tools/quality_gate.sh build system`
- **합격 기준: 요구사항 커버리지 100%** (모든 SWR/SSR이 *통과한* 시스템 테스트에 `@trace`됨, `tools/check_requirements_coverage.py`) **+ 테스트 성공률 100%**
- 완료 후 `aspice-reviewer` 서브에이전트(`review` 스킬, 체크리스트 ST)로 리뷰한다.

## 결과 보고

- 생성한 케이스 수와 저장 경로
- SWR별 케이스 수와 사용한 기법
- 생성 조건 1~10 점검 결과 (미충족이면 이유)
- 요구가 모호하거나 누락되어 케이스를 만들 수 없었던 부분과 OEM 질의 제안
